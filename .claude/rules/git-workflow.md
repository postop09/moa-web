# Git 워크플로

## 커밋
- 하나의 커밋은 하나의 논리적 변경만 담는다. 포맷팅/리팩터링과 기능 변경은 분리한다.
- 형식: `<type>(<scope>): <subject>`
  - type: feat, fix, refactor, docs, test, chore, perf, style, ci, build
  - scope: 모듈/디렉터리명 (예: auth, api, ui). 명확하지 않으면 생략 가능.
  - subject: 50자 이내, 명령형, 마침표 없음. 예: `feat(auth): 소셜 로그인 추가`
- 하위 호환이 깨지는 변경은 `feat(api)!: ...` 처럼 `!`를 붙이고 본문에 `BREAKING CHANGE:` 를 명시한다.
- 본문에는 "무엇"보다 "왜"와 영향 범위를 적는다. 이슈가 있으면 `Refs #123`, 종료 시 `Closes #123`.
- 커밋 전 확인: 관련 테스트 통과, 린트 통과, 디버그 코드·불필요한 파일 미포함.
- 커밋 메시지는 Claude가 작성하되 사용자 확인 후 커밋한다. `--no-verify` 는 사용하지 않는다.
- 자동 생성 파일(lock 파일, 빌드 산출물, 스냅샷)은 의도한 변경일 때만 커밋에 포함한다.

## 브랜치
- `main`: 항상 배포 가능한 상태. 직접 커밋/푸시 금지.
- `feature/<이슈번호>-<짧은설명>`: 기능 개발
- `fix/<이슈번호>-<짧은설명>`: 버그 수정
- `chore/<짧은설명>`: 설정, 의존성, 문서 등 비기능 작업
- `hotfix/<이슈번호>-<짧은설명>`: 프로덕션 긴급 수정 (main에서 분기, main과 develop에 모두 머지)
- 작업 시작 전 최신 `main`에서 분기하고, 오래된 브랜치는 `rebase`로 최신화한다.
- 이미 push한 공유 브랜치는 `rebase`/`force push` 하지 않는다.
- 머지된 브랜치는 삭제한다.

## PR
- 제목은 커밋 메시지 규칙과 동일하게 작성한다.
- 하나의 PR은 리뷰 가능한 크기(변경 300줄 내외)를 유지한다. 크면 나눈다.
- 설명에 포함: 변경 요약, 변경 이유, 테스트 방법, 스크린샷(UI 변경 시), 관련 이슈, 리뷰어가 특히 봐야 할 지점
- 초안 단계는 Draft PR로 열어 방향을 먼저 공유한다.
- 리뷰어 1명 이상 승인 + CI 통과 + 충돌 해결 후 머지한다.
- 머지 방식: `Squash and merge` 기본. 커밋 히스토리를 보존해야 할 때만 `Rebase and merge`.
- 리뷰 코멘트에 대한 수정은 새 커밋으로 push하고, 머지 시 squash로 정리한다.

## 되돌리기
- 이미 머지된 변경을 되돌릴 때는 `git revert`를 사용한다. 히스토리 삭제 금지.
- 잘못된 커밋을 발견하면 임의로 수정하지 말고 먼저 알린다.
